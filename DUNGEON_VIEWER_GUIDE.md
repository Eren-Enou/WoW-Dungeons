# Dungeon Viewer guide (0.8)

The viewer shows a dungeon's environment without playing it. It needs no
party, no portal and no fights. It draws with **the game's own renderer**
(`crates/game/src/env.rs`), so what you see is what the game draws.

* It never creates a simulation.
* It never writes your save. `--viewer-test` checks this.

It reads ordinary dungeon files, handwritten or generated by Dungeon Forge.

## Opening it

From the packaged build (PowerShell, in the extracted folder):

```powershell
.\dungeon-sandbox.exe --viewer                       # the dungeon selected in the hub
.\dungeon-sandbox.exe --viewer hollow_reliquary      # by id
.\dungeon-sandbox.exe --viewer assets\content\variants\forge\hollow_reliquary_s10.toml   # by file
.\dungeon-forge.exe view assets\forge\blueprints\hollow_reliquary.toml --seed 7          # generate + open
```

`Dungeon Viewer.bat` in the package does the first one; you can drop a
dungeon file onto it.

From the repository (development):

```powershell
cargo build --release --workspace
.\target\release\dungeon-sandbox.exe --viewer emberforge_vaults
.\target\release\dungeon-forge.exe view assets\forge\blueprints\emberforge_vaults.toml --seed 12 --layers structure,modules
```

In the game, the hub's **Dungeons** tab has **Inspect in viewer (V)**
(or press V). It opens the selected dungeon. **Backspace** in the viewer
returns to the hub.

Set `DUNGEON_SAVE_DIR` to a scratch folder when you script runs, as for the
other developer flags. The viewer reads the profile only to know the hub's
selection.

### Command-line options

| Option | Effect |
|---|---|
| `--viewer [ID or FILE]` | Start in the viewer |
| `--blueprint FILE --seed N` | Generate that layout first (with `dungeon-forge`) and open it |
| `--room NAME` | Start at a room (its id, e.g. `r6`, or its name) |
| `--layers a,b,...` | Switch layers on at start: `nav`, `collision`, `structure`, `encounters`, `modules`; `noui`, `noinfo` hide panels; `panels` keeps them in a tour; `map` opens the 2D map; `inspect` turns inspection lighting on |
| `--viewer-tour` | Screenshot every room and corridor (overview), plus an eye-height view inside every room, the 2D map (`map.png`) and the whole dungeon from above with atmospheric and inspection lighting (`overhead_atmospheric.png`, `overhead_inspection.png`). Writes `screenshots/viewer/<id>/index.html` (a contact sheet) and `stats.csv` (frame time and meshes per shot), then exits |
| `--viewer-test` | Scripted check of the controls (see "Verification"); exits 0 when all pass |
| `--no-vsync` | Uncapped frame rate, for frame-time measurements |

## Flight speed and camera (0.8.1)

The bar at the bottom centre shows the flight speed in m/s and its preset
band ("slow" below 6 m/s, "normal" below 25, "fast" above). Its buttons do the same as the
keys: Slow 7, Normal 8, Fast 9, − and +, Map M, Light I.

* **Speed range:** 0.5 to 200 m/s. Shift and Ctrl multiply it while held.
* **Smoothing:** flight eases in and out (about 0.1 s), so short taps still
  move precisely. Walk and orbit modes are unchanged.
* **Near walls:**
  * walk mode keeps the eye over walkable floor, which stays 0.4 m from
    walls, so it never clips;
  * free flight passes through walls, pillars and arches on purpose, so you
    can inspect from anywhere. The near plane is 0.1 m, so geometry only
    disappears when the camera is effectively inside it.

**Preferences.** The speed and the inspection-lighting setting are remembered
for the session. When you leave the viewer they are saved to `viewer.toml`,
next to the save file (in `DUNGEON_SAVE_DIR` when set). This is a separate
file: the player save is never read or written by the viewer.
`--viewer-test` and `--viewer-tour` never write it.

## The 2D map (0.8.1)

M opens a top-down map of the whole dungeon. It is a developer view, not a
player map.

**What it shows:**
* **Floors**, shaded by height (light high, dark low); lava is red.
* **Room and corridor outlines**, coloured by purpose. 0.9 files say why
  every room exists; older files are classified from their route data.
  Labels carry the purpose's letter (`r12:R`).
  * blue: main route;
  * gold, R: reward detour (an optional fight and/or a cache, rejoining
    further on);
  * rose, F: tactical flank (a side passage into a required pack's room);
  * cyan, S: safe way round a hazardous crossing;
  * red, !: the hazardous crossing itself (main corridors with vents);
  * green, O: optional encounter chamber;
  * yellow, C: treasure cache chamber;
  * pale blue, V: landmark (no reward);
  * violet, Q/E: quiet chamber (deliberate) or empty side chamber (0.8 files);
  * orange, D: overlook and its one-way drop;
  * pink, L: return loop;
  * cyan, A: alternate route with no declared purpose (0.8 files);
  * grey: passage.
* **Branches** (0.9) as dashed lines in their purpose's colour, from the main
  room they leave to the one they rejoin.
* **Hazards** as red rings at their real radius; **caches** as gold diamonds.
* **Doorways** in yellow, and the **main route** as a dashed line.
* **One-way drops** as orange arrows.
* **Spawns** by rank (magenta boss, yellow elite, white trash), with a green
  ring for optional packs.
* **The entrance** (green dot) and **the camera** (red square, with dots for
  its heading).

**Room labels:** ids when fitted, names once zoomed in, and role, purpose,
floor height and encounter close up.

**Controls:**

| Input | Action |
|---|---|
| Mouse wheel | Zoom about the cursor |
| Left drag | Pan |
| Left click | Fly the 3D camera to that room and close the map |
| F | Fit the whole dungeon |
| M or Esc | Close |

The map is drawn from the same nav and room data as the 3D view, inside the
game: the game does not use the forge's SVG code. It is rebuilt on F5 and on
[ / ].

## Inspection lighting (0.8.1)

Why distant rooms fade from above: each room's atmosphere uses linear
distance fog, typically 18–75 m. It is not far-plane clipping (the far plane
is 1000 m), and it is not culling (only off-screen meshes are culled).

I switches to inspection lighting:
* neutral white ambient light;
* fog pushed beyond 5 km.

The whole dungeon is then readable from any height. Press I again to return
to the room-by-room atmosphere. It changes only the viewer's camera and
lights: the dungeon file, the simulation and normal play are never affected.
In a dungeon run, the atmosphere always applies.

## What the layers show

1. **Navigation**:
   * walkable surfaces outlined, coloured by height (blue low, yellow high),
     with name and elevation labels;
   * walk portals (green) and one-way drops (orange arrows);
   * areas the entrance can't reach in **magenta**, labelled "NOT REACHABLE",
     unless the file marks them `unreachable`. The info panel warns too.
2. **Structure**:
   * room and corridor bounds, coloured by purpose, as on the 2D map;
   * doorways (yellow frames);
   * the main route as arrows;
   * room labels with id, role and route.

   Generated dungeons carry their rooms (`[[dungeon.rooms]]`). In handwritten
   ones, rooms are derived from area names ("Hall (aisle 2)" belongs to
   "Hall").
3. **Encounters**:
   * every spawn as a sphere by rank (white trash, yellow elite, magenta
     boss);
   * aggro radii (red; green for optional encounters);
   * patrol routes and hazards (orange);
   * encounter labels.

   No simulation runs; this is the file's data.
4. **Modules and anchors**:
   * every modular piece's bounds (blue; red when its model file is missing
     and the procedural fallback is drawn);
   * every decoration anchor with its facing (green if something was placed
     there).

## The panels

* **Info (top left)**:
  * name and id; where the dungeon came from;
  * blueprint, seed, kit and generator version (generated dungeons);
  * counts of rooms, corridors, doorways, areas, encounters and enemies;
  * modules, including fallbacks;
  * reachability warnings;
  * camera position and mode;
  * the room, area and floor height under the camera;
  * layer states and the selection.
* **Status (bottom right)**: frame time (mean and 95th percentile), visible
  and total meshes, entities.
* **Selection**:
  * a room:
    * role, route, order;
    * purpose; whether it is a dead end; how many rooms it lies off the main
      route;
    * the branch it belongs to (0.9): purpose, the rooms it joins, what it
      holds, what it bypasses (always nothing required), and what the
      generator measured (walking lengths, flank angle and staging margin,
      vents on the short way), with any warnings;
    * size, floor heights, areas, doorways;
    * encounter, atmosphere preset;
  * a module: kind, asset path (and whether it fell back), position, yaw,
    scale, bounds, room;
  * an anchor: kind, position, facing, room, clearance and what was placed;
  * a mob: template, encounter, rank, aggro radius, patrol points.

  The viewer is read-only: nothing can be edited yet.

## A visual inspection workflow

1. Generate:
   `dungeon-forge generate assets/forge/blueprints/hollow_reliquary.toml --seed 7`.
   Or skip this and use step 2's `view` form.
2. Open it: `dungeon-forge view assets/forge/blueprints/hollow_reliquary.toml --seed 7`.
3. Fly through it with Tab (room by room) or L (list); G to stand in a room.
4. Press 1 for navigation, and check that walls and floors match the outlines.
5. Press 4 for modules and anchors; click a piece to inspect it.
6. Press ] to compare the next seed, and [ to go back.
7. Press F12 for screenshots, or run a tour:
   `dungeon-sandbox --viewer forge_out/hollow_reliquary_s7.toml --viewer-tour`
   and open `screenshots/viewer/hollow_reliquary/index.html`.
8. Note problems: gaps, overlaps, walls in doorways, floating decoration.
9. Change the kit (`assets/forge/kits/*.toml`: `[modules]`, `[[decorate]]`,
   `[atmosphere.*]`) or a model (`scripts/make_prop_models.py`).
10. Regenerate (] then [, or `generate` again) and press F5 to reload.

## Verification

`--viewer-test` presses the real keys and checks:
* entering;
* R/Home: near the entrance;
* Tab: a room jump;
* W: flight;
* G: walk mode stays 1.7 m over walkable floor;
* 1–4: the layers switch on;
* F12;
* 7 and M:
  * the slow preset;
  * the map opens;
  * a room's position on the map leads back to that room;
* 9 and =: the fast preset, then one step up (51.75 m/s);
* I: inspection lighting (ambient 650, fog pushed away);
* I again: the atmosphere returns;
* F5: reload, with the camera kept;
* ]: on generated dungeons, the next seed is generated and loaded, and the
  map is rebuilt;
* Backspace: back to the hub.

It then prints a report and exits 0 when all checks pass. Results for 0.8
and 0.8.1 are in PROGRESS.md.

## Branch purposes

Purposes come from the generator (0.9: `[[dungeon.branches]]`, measured on
the navigation; DUNGEON_REMIX_0_9.md). BRANCH_PURPOSE_0_8_1.md is the review
that led to them.

This is developer knowledge. Players see only the doorway clues (a teal
tablet or a white-hot gate lamp where a branch holds something, a dim candle
or ember lantern at a side passage, warm light at the way to a landmark) and
the caches themselves.

## Remixed layouts (0.9)

When the hub's Layout row has a remix or a seed chosen for the selected
dungeon, V (or "Inspect in viewer") opens that generated file, so you can
look at the layout before playing it. The file lives in `generated/` beside
the save.
