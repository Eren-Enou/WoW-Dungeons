# Dungeon Sandbox — Claude Code project instructions

## Mission
Develop a standalone playable Rust + Bevy 0.20 third-person dungeon sandbox inspired by the *mechanical feel* of classic tab-target MMORPG dungeons. This is an original implementation, not a WoW client, private server, or asset extractor.

## Priorities (in order)
1. A working executable that a human can play.
2. A complete hub -> recruit -> dungeon -> boss -> rewards -> hub loop.
3. Autonomous tank, healer and DPS agents.
4. Deterministic, testable combat simulation and data-driven encounters.
5. Visual polish only after the loop works.

## Current scope (as of 0.9.1)
- One hub, seven original dungeons (including The Cinderdeep Hollows, the 0.5 lava cave; The Emberforge Vaults and The Hollow Reliquary, generated by Dungeon Forge from the volcanic and crypt kits; and the Cavern Traverse navigation test level) and one 10-player raid, all data-driven TOML (`assets/content/dungeons/`); primitive meshes and materials.
- Layered 2.5D navigation (`crates/sim/src/nav.rs`, `poly.rs`; NAVIGATION_0_4.md, DUNGEON_0_5.md): areas are convex polygons with heights, ramps in any direction, decks and authored one-way drops; they connect only where they overlap and are level. Actors carry `y` and a surface; range, line of sight, ground effects and aggro are elevation-aware. The renderer (`dungeon.rs`, `cave.rs`) builds geometry, decor, lava and lights from the same data. Rectangle maps must stay bit-identical in navigation.
- One player-controlled character plus 4 (party) or 9 (raid) autonomous companions with selectable AI profiles; four classes (Warden tank, Mender healer, Striker melee, Arcanist ranged) with five abilities each.
- Classic MMO controls (`crates/game/src/controls.rs`), clickable party/raid frames with mouseover healing, threat-aware nameplates, an action bar driven by `Sim::ability_state`, and tooltips generated by `dungeon_sim::describe`.
- Combat model, AI, progression (levels, gear, vendor), sandbox overrides and an encounter editor already exist; RULES.md is the authority for formulas. Patrols and line-of-sight pulses (0.7) are opt-in through data; the cover AI and parked-DPS retarget are measured in DUNGEON_FORGE_0_7.md.
- Playtesting: earlier versions have been played by the maintainer, without written notes. Keep automated verification and human evaluation separate in docs; write "not covered by a recorded human playtest" rather than claiming nobody played it, and never claim a playtest that didn't happen.
- Dungeon Forge (`crates/forge`, `dungeon-forge` CLI; DUNGEON_FORGE_0_6.md, DUNGEON_FORGE_0_7.md): blueprints (intent, `[identity]` challenges) + kits (theme libraries: spatial components, templates, Recipes 2.0, loot, palette) + seed → validated ordinary dungeon TOML. `dungeon-forge report` finds where parties die or dither; `--overrides` is a proof of concept for keeping designer edits. Bevy-free; the game and sim never depend on it. Generated files are regenerated, not hand-edited, unless they stop being regenerated. Keep output deterministic (bump `GENERATOR_VERSION` when output for the same seed changes) and keep every generated layout passing the loader, the structure checks and the encounter-space checks. A blueprint's promised challenges must be delivered by tagged recipes.
- Dungeon Remix (0.9; DUNGEON_REMIX_0_9.md): every branch a blueprint asks for has a purpose (`[[routes]]` detour/flank/safe, `[[side]]` optional/cache/vista/quiet) and `purpose.rs` measures on the navigation that it delivers it (walking lengths, flank angle and aggro-free staging, hazard coverage, rewards, no bypassed required fight, drops that save walking, final boss reachable), or the attempt is rejected; facts go into `[[dungeon.branches]]`. Never let a branch go round a required encounter or a boss. `dungeon-forge audit` (purposes over 100+ layouts) and `dungeon-forge routes` (scripted leader, companions on their own AI) are the evidence; claims about a choice need `routes` numbers, and a flank or safe way that the numbers show to be worse or neutral is reported as such. Kit recipes carry a measured `flank` rating (0.9.1) that steers flank targets; change a rating only with new `routes` evidence. Treasure caches (`[[dungeon.caches]]`) are read by the sim (opened by walking up, loot like a cleared encounter). Companions walk the leader's trail when their formation slot is hidden from the leader or inside an idle pack's aggro. The hub offers Classic/Remix/Seed for forge dungeons by running the external `dungeon-forge` into `generated/` beside the save; the game still never links the forge crate.
- Dungeon viewer (0.8, `viewer.rs`; DUNGEON_VIEWER_GUIDE.md): `--viewer [ID|file]` or V in the hub; no `Sim`, no saves. The environment is built once for both play and viewer in `env.rs` (+ `modules.rs`, `structure.rs`): never add viewer-only visuals or a second renderer. Check viewer changes with `--viewer-test` and `--viewer-tour` (contact sheet, frame stats).
- Modular environments (0.8; MODULAR_ENVIRONMENTS.md): kit `[modules]` pieces follow navigation walls, doorways and pillar holes; `[[decorate]]` rules place props at forge anchors; `[atmosphere.*]` presets blend per room. Art never changes walkability or line of sight: walls are navigation's walls, openings stay walkable, mounted pieces hang above 2.2 m (tests in `modules.rs`). Presentation changes must keep simulation hashes identical.
- Props (`[[dungeon.props]]`, GLB under `assets/models/` with a primitive fallback) are scenery only; every model needs a row in `assets/models/PROVENANCE.md`. Never add Blizzard or other game-extracted assets, and never require a game client.
- Windows distribution: `scripts/package-windows.ps1` (RELEASE_BUILD.md). Never push or publish a release without explicit authorization.
- Prefer making the game better to play over making it bigger: no new dungeons, classes, talent trees or balance redesigns unless a milestone asks for them.
- No networking, accounts, payments, procedural large world, LLM calls for NPC decisions, original Blizzard assets, or exact retail parity.

## Engineering conventions
- Rust stable, pin Bevy to version 0.20.x and pin dependency versions with Cargo.lock. Confirm documented APIs against the pinned version.
- Organize simulation rules separately from rendering and UI; make simulation callable from a headless runner.
- Prefer safe Rust. No unsafe except with explicit reason and tests.
- Fixed simulation timestep; seeded random number generator for reproducibility.
- Data-driven dungeon and encounter configuration with schema validation and actionable error messages.
- Do not silently implement placeholder behavior while claiming feature completion.
- Use original names, maps, models, audio and texture assets. Use primitive stand-ins early.
- Do not import or translate GPL/proprietary source into this repository without explicit authorization and license review. Studying behavior is permitted; record all referenced material in RESEARCH.md.

## Mandatory iteration loop
For each milestone: implement the smallest coherent slice, run `cargo fmt --all -- --check`, `cargo check --workspace`, `cargo test --workspace`, then `cargo clippy --workspace --all-targets -- -D warnings` when feasible. UI work: also run the automated graphical checks (`--input-test`, `--frame-test`, `--tooltip-test`, `--click-test`, `--hub-tour`, `--demo --level N --screenshots`, `--area-tour` for level work, `--viewer-test`, `--remix-test`) with `DUNGEON_SAVE_DIR` pointing at a scratch folder, and look at the screenshots. Navigation/AI work: compare 100+ seed headless batches of every dungeon against the previous build (watch wins, deaths, `nav stuck`, `unreachable`, `dithers`), run `dungeon-forge test <blueprint> --layouts 1..10` over generated layouts, `dungeon-forge audit <blueprint> --layouts 1..100` for branch purposes and `dungeon-forge routes` for route choices, and use `--nav-debug` screenshots. Claims of behaviour-neutral changes need identical per-seed event-log hashes (`--json` `log_hash`) against the previous build. Gate checks on exit codes, never through a pipe such as `| tail` that hides failures. Fix failures, rerun checks, and update PROGRESS.md with what was actually verified. Manually launch the graphical game where supported; if the environment cannot verify graphics, explicitly report that limitation and give user smoke-test steps.

## Autonomy
Make reasonable design decisions independently. Don't block on minor cosmetic choices. Keep work within project folder. Do not run destructive commands, install untrusted scripts, change system settings, or request elevated privileges. Do not use broad permission bypass. When stuck, reduce scope to a working vertical slice, record the obstacle and continue with another unblocked milestone. Never claim tests passed unless run.

## Project state
Read SPEC.md, TASKS.md, REFERENCES.md and PROGRESS.md at the start of each session. Keep PROGRESS.md truthful and current. A task is complete only if its documented acceptance test passes.
